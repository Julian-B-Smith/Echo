- **Why:** the human doubted Echo needs four fixed controls and wanted Time in the row as a scale centred on the
  sound's own time (Sluice's shape). `time.ms` does nothing while synced and `time.div` is stepped, so the row's Time

- **A scale send is a move only if it moves a time.** `applied(kTimeScale)` compares the resolved targets before and
  after. A re-sent scale, or a synced scale wandering inside one octave's snap band (0.707 – 1.414 for ×1), changes no
  target; marking it a control move anyway would turn a tempo move in flight into a key move (the cls = 1 re-latch to
  `time.change`, stepHead) for a sample, and a host that re-sends its fixed controls every block would do it
  continuously. The plant `scaleResendIsMove` is that fault.

    0.05735768128462411): it does not follow time.change".

  - **L1, the snap tie.** At s = 0.35355339059327379 (horde's log law at knob 0.125) `log2` returns exactly -1.5 and
    `lround` gave x1/4; the nearest octave is x1/2. The engine no longer uses log2: `timeScale` does a mantissa
    compare, `frexp` then `m >= sqrt2 / 2`, which is exact (the boundaries 2^(k + 1/2) are irrational, so no double
    is a tie; the double nearest each, sqrt2 x 2^k, is just above and snaps up; the old "a tie cannot occur" comment
    was false for the rounded log and is rewritten). This differs from the brief's suggestion (compare s*s with
    2^(2k+1)): the product s*s is itself rounded, so near a boundary that compare is not exact either. The
    REFERENCE in the test does use s^2 vs 2^(2k+1), exactly (the rounded product plus its fma residual), so it
    shares neither method nor libm with the engine. `scaleResolution` gains the double nearest each boundary and one
    ulp either side (12 cases x 2 rates) and the hand case 0.35355339059327379 -> 0.25 s. Plant `scaleSnapRounds`
    (round(log2 s)) -> "synced the double nearest a boundary (x0.353553391) at 44100 Hz: resolved 0.125000000 /
